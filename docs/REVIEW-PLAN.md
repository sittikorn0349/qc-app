## 1. สิ่งที่ต้องแก้ก่อนทำอย่างอื่นต่อ (Blocker)

### 1.1 เอกสารจาก form builder (`pwa-forms.js`) ไม่อยู่ใน backup / ส่งเอกสาร / sync เลย
**สถานะ: CRITICAL — เสี่ยงข้อมูลหายแบบผู้ใช้ไม่รู้ตัว**

- `pwa-forms.js` เปิดฐานข้อมูลของตัวเอง (`indexedDB.open('qc-forms',1)`, บรรทัด 29) แยกจาก `qc-offline` / `qc-online-*`
- `buildBackup()` ใน `index.html` (บรรทัด ~588) อ่านจาก `records` / `trashRecs` เท่านั้น
- `pwa-send.js` ใช้ `window.__qcDocs()` เท่านั้น
- **ไม่มีจุดใดในโค้ดเบสเชื่อม `qc-forms` กับ backup/send/sync** — ตรวจแล้วด้วย `grep` ยืนยัน

**งานที่ต้องทำ**
- [x] เลือกทาง: (ก) รวม `pwa-forms` เข้า data model เดียวกับฟอร์มตรวจงาน หรือ (ข) ถ้าจะคงแยกฐานข้อมูลไว้ก่อน ให้แก้ `buildBackup()` และ `pwa-send.js` ให้ดึงจากทั้งสองฐานข้อมูล
  - **ทำแล้ว (ข):** backup มี `formDocs`, `customForms`, `form-photos/` · `QC.restoreForms()` กู้คืน (ฉบับในเครื่องที่ใหม่กว่าไม่ถูกทับ) · ส่งเอกสารมี `forms.json` ตรวจ hash และนับในรหัสยืนยัน
- [x] เพิ่มเอกสารจาก form builder ให้ขึ้นใน "คลังเอกสาร" หน้าเดียวกับฟอร์มตรวจงานหลัก (ปัจจุบันแยกที่เก็บ = แยกหน้าตา UI ด้วย) — ส่วน “รายงานแบบอื่น” ในคลังเอกสาร ค้นหาได้
- [x] ก่อนปล่อยให้ผู้ใช้จริงสร้าง custom form ได้ ต้องปิดช่องนี้ก่อน — ยิ่งมีฟอร์มชนิดใหม่ ยิ่งขยายข้อมูลที่ไม่ถูกสำรอง
  - ซิงก์ขึ้น Supabase: โค้ดเสร็จแล้ว (`form_docs`, `form_templates`) · **ต้องรัน `supabase/migrations/20261123000005_form_docs_zones.sql`** ระหว่างนี้แอปบอกว่า “ในเครื่องนี้เท่านั้น ยังไม่ซิงก์”

### 1.2 การนำทางหน้าแรกผูกกับ regex จับข้อความสถานะภาษาไทย

## 5. สถาปัตยกรรมคู่ขนาน (Hybrid): ครั้งแรกต้องมีเน็ต จากนั้นใช้ออฟไลน์ได้

**หลักการที่ตกลง**: เน็ตจำเป็น**เฉพาะตอน setup ครั้งแรกต่อเครื่อง** หลังจากนั้นแอปต้องใช้งานได้แม้ไม่มีเน็ตต่อเนื่องหลายวัน โดยไม่กระทบการสร้าง/แก้ไขฉบับเลย — นี่คือจุดที่ต้องออกแบบให้แยกชัดจาก "ความพร้อมของ session/token" เพราะทั้งสองเรื่องนี้เป็นคนละปัญหากัน

### 5.1 ขั้น Setup (ต้องมีเน็ต ทำครั้งเดียวต่อเครื่อง)

เมื่อ login ผ่าน Google OAuth สำเร็จครั้งแรก แอปต้องดึง**ทุกอย่างที่จำเป็นต่อการทำงานออฟไลน์**มา cache ไว้ล่วงหน้า ไม่ใช่ fetch-on-demand แบบที่โค้ดปัจจุบันทำ (`beta/pwa-shell-online.js` เรียก Supabase ตรงเมื่อต้องใช้ข้อมูล ซึ่งจะพังทันทีถ้าไม่มีเน็ต):

1. โปรไฟล์ผู้ใช้ + รายชื่อโปรเจกต์ที่เป็นสมาชิก + สิทธิ์ (role) ในแต่ละโปรเจกต์
2. รายชื่อสมาชิกทั้งหมดของโปรเจกต์ (จำเป็นสำหรับ dropdown "มอบหมายให้" ที่ `assignRow()` ใช้อยู่แล้ว)
3. โครงฟอร์มทั้งหมดที่ใช้ได้ในโปรเจกต์ — ทั้ง built-in (`BUILTINS` ใน `pwa-forms.js`) และ custom form ที่สร้างไว้แล้วในระบบ
4. โฟลเดอร์/เอกสารที่มีอยู่แล้วในโปรเจกต์ (เท่าที่จำเป็นสำหรับการเปิดงานต่อ)
5. บันทึก flag `qc-setup-done=1` พร้อม timestamp ลง localStorage เป็นสัญญาณว่า "เครื่องนี้พร้อมทำงานออฟไลน์แล้ว"

ถ้า setup ล้มเหลวกลางทาง (เน็ตหลุดระหว่างดึงข้อมูล) ต้อง**ไม่ตั้ง flag ว่าสำเร็จ** และบอกผู้ใช้ตรงๆว่ายังต่อเน็ตไม่สำเร็จ ให้ลองใหม่ ไม่ใช่ปล่อยให้เข้าหน้าฟอร์มทั้งที่ cache ไม่ครบ

### 5.2 หลัง Setup (ออฟไลน์ได้เต็มรูปแบบ)

- การเปิดแอปทุกครั้งหลังจากนี้ **ต้อง render จาก local cache ก่อนเสมอ** ห้ามมีจุดใดใน bootstrap logic ที่ `await` การเช็ค network/session ก่อนแสดงหน้าฟอร์ม (ถ้ามี cache พร้อมใช้) — เช็ค session เป็นงาน background ที่ทำคู่กันไปได้ ไม่ใช่ gate ก่อนแสดงผล
- การสร้าง/แก้ไขฉบับเขียนลง IndexedDB + outbox ก่อนเสมอ (ของเดิมมี pattern นี้อยู่แล้วใน `pwa-shell-online.js`) — ส่วนนี้ไม่ต้องรอ session valid เลย เพราะเป็น local write ล้วนๆ
- **แยกให้ชัด**: "เขียนข้อมูลใหม่ในเครื่องได้" (ไม่ผูกกับ token) กับ "sync ขึ้นเซิร์ฟเวอร์ได้" (ต้องมี session valid) เป็นสองสถานะอิสระกัน — ถ้า token หมดอายุระหว่างออฟไลน์นาน ผู้ใช้ต้องยังกรอกฟอร์ม ถ่ายรูป บันทึกต่อได้ตามปกติ แค่ sync ค้างไว้ในคิว (outbox) รอ refresh token ตอนมีเน็ต
- ถ้าเครื่องนั้น**ไม่มี flag `qc-setup-done`** (ยังไม่เคย setup) และไม่มีเน็ต → ต้องมีหน้าข้อความเฉพาะ "เครื่องนี้ยังไม่เคยเชื่อมต่อ ต้องมีเน็ตก่อนใช้งานครั้งแรก" ที่ชัดเจน ไม่ใช่ error ทั่วไปหรือจอขาวที่หาสาเหตุไม่ได้

### 7.5 ทิศทางแก้ไข (เรียงจากทำง่าย → ทำยาก)

**แก้ 7.1 (แถวรายการหนาแน่น/ไม่มีโหมดกรอกเร็ว)**
- [x] **ขั้นต่ำ (CSS/JS ล้วน ไม่แก้ data model)**: เพิ่มปุ่ม "ไปรายการที่ยังไม่ตรวจถัดไป" แบบ floating ที่มุมจอ — หาด้วย `state.items` ตัวแรกที่ `!it.res` แล้ว `scrollIntoView` เหมือนที่ `appendItems()`/`$('#add')` ทำอยู่แล้วตอนเพิ่มรายการใหม่ (ใช้โค้ด pattern เดิม)
- [x] **ขั้นกลาง**: ทำ auto-advance หลังกดผลตรวจ (ปุ่ม `ผ่าน/ต้องแก้ไข/ไม่ผ่าน` ใน `seg` ของ `row()`) ให้เลื่อนไปโฟกัสที่รายการถัดไปที่ยังไม่ตรวจอัตโนมัติ ไม่ต้องรอผู้ใช้เลื่อนเอง — แก้ที่ event handler ของปุ่ม `RES` ใน `row()` (`index.html` ส่วน `seg.appendChild`)

**แก้ 7.3 (ไม่มีกรอกด้วยเสียง)**

- [ ] **ขั้นสูง (ควรทำคู่กับหมวด 8.1)**: ให้ PM อัปโหลดรูปแปลน/ผังต่อโปรเจกต์ แล้วผู้ตรวจแตะจุดบนรูปเพื่อ pin ตำแหน่ง — เทคนิค canvas/pointer-event ที่ใช้ทำฟีเจอร์ "ขีดเขียนบนรูป" ใน beta (`annotate()` ใน `beta/index.html`) ใช้ซ้ำได้เกือบทั้งหมด เปลี่ยนแค่ภาพพื้นหลังจากรูปถ่ายเป็นรูปแปลน และเก็บพิกัด pin แทนรูปทรงวาด — ควรทำหลังแก้โครงสร้าง backup/sync ตามหมวด 1.1 เพราะไฟล์แปลนจะเพิ่มขนาดข้อมูลที่ต้อง sync อีกชั้น

## 8. วิจัยฟีเจอร์ใหม่จากคู่แข่งในตลาด (เทียบปี 2026)

เทียบกับแอป punch-list/site-inspection ที่ได้รับการจัดอันดับสูงปี 2026 (Fieldwire, Procore Quality & Safety, SafetyCulture/iAuditor, Raken, SnagBricks, PlanRadar) — ที่มา: การค้นเว็บวันที่ตรวจเอกสารนี้

| # | ฟีเจอร์ที่ขาด | คู่แข่งที่มีอยู่แล้ว | เหตุผลที่ควรมี |
|---|---|---|---|
| 8.1 | Pin ปัญหาบนแปลน/ผัง ไม่ใช่แค่พิมพ์ตำแหน่งเป็นข้อความ | Fieldwire (plan viewer ออฟไลน์ + markup), PlanRadar, Procore | เพิ่ม precision หาจุดหน้างานจริง ต่างจาก location free-text ของ qc-app มากที่สุด |

| 8.3 | คลัง template เช็กลิสต์ที่หลากหลายกว่า / no-code กว่า | SafetyCulture ("best template library") | form builder ของ qc-app เป็นทิศทางถูกแล้ว แต่ยังไม่มี "ตลาด" ให้เลือกเพิ่มเอง |
| 8.4 | Dashboard/analytics เชื่อม inspection → corrective action | Procore Quality and Safety | ฟิลด์ assignment/due-date ใน beta เป็นจุดเริ่มดี แต่ยังไม่มีสรุปเช่น "ผู้รับเหมาไหนค้างแก้มากสุด" |

| 8.6 | ลายเซ็นวาดด้วยนิ้ว ไม่ใช่แค่พิมพ์ชื่อ | มาตรฐานในแอปคู่แข่งเกือบทั้งหมด | ส่วน "สรุปผลและลงนาม" ของ qc-app ให้พิมพ์ชื่อเท่านั้น น้ำหนักความน่าเชื่อถือของเอกสารต่ำกว่า |

**ฟีเจอร์ที่ qc-app ทำได้เกินมาตรฐานตลาด**: ระบบ verify-before-write (SHA-256 + two-phase commit ตอนรับไฟล์) — ไม่มีคู่แข่งรายใดโฆษณาความแน่นหนาระดับนี้ และ "ตรวจซ้ำหลังแก้ไข" ที่มีอยู่แล้วก็เทียบเท่า two-step verification ของ Fieldwire

**ลำดับความสำคัญ**: ฟีเจอร์ในหมวด 8 ทั้งหมดควรทำ**หลัง**แก้ข้อ 1.1 (form builder หลุดจาก backup) เสร็จแล้วเท่านั้น เพราะทุกฟีเจอร์ใหม่ (โดยเฉพาะ 8.1, 8.2, 8.3) จะขยายปริมาณข้อมูล/ไฟล์ที่ต้อง backup-send-sync ให้ครบ — ถ้าเพิ่มก่อนแก้โครงสร้างเดิม จะเพิ่มขนาดของปัญหาเดิมให้ใหญ่ขึ้นไปอีก

## 9. สิ่งที่ทำในรอบนี้ (หมวด 7–8) และที่ยังค้าง

- **8.6** เซ็นชื่อด้วยนิ้วทั้ง 3 ฝ่าย เก็บเป็นรูปในฉบับ ขึ้นใน PDF · ใส่วันที่ให้อัตโนมัติ · นับใน hash ของการส่งเอกสาร

### รอบล่าสุด (ตามเอกสารสรุปจุดแข็ง/จุดอ่อน)
- **8.1 ระบุตำแหน่งบนแบบแปลน (ไม่บังคับ)**: ลิงก์ในช่องตำแหน่งของแต่ละรายการ และเมนู ⋯ ของฟอร์ม · เพิ่มรูปแบบ (ย่อเหลือด้านยาว 2400 px) หรือเลือกแบบที่มีในโครงการแล้ว · แตะวางหมุดเลขรายการ, แตะหมุดตัวเองเพื่อลบ, ขยาย/ย่อ, ไปรายการก่อน/ถัดไป · “พิมพ์แผ่นแผนผังสำหรับช่าง (A3)” เฉพาะจุดที่ยังต้องแก้ (หรือทุกจุด) พร้อมตารางติ๊กว่าแก้เสร็จ · ตรวจรอบใหม่พาหมุดของรายการค้างไปด้วย
  - ข้อมูล: `plan={sheets:[{a,name,w,h}],pins:{itemId:[{s,x,y}]}}` เก็บในฉบับ · ออนไลน์อยู่ใน `inspections.extra.plan` (ไม่ต้องแก้ schema) · รูปแบบเข้าไฟล์สำรอง ส่งเอกสาร อัปโหลด และไม่ถูกลบเป็นรูปที่ไม่มีใครใช้
- **ความครบของข้อมูล**: หน้า “ข้อมูลของคุณเก็บไว้ที่ไหน” ในเมนูสำรองข้อมูล บอกแต่ละชนิดข้อมูลว่าอยู่ที่ไหน (ซิงก์ / ไฟล์สำรอง / ในเครื่องนี้เท่านั้น) และแถวที่ยังไม่ปลอดภัยเป็นสีเตือน · ตัวเตือนสำรองนับรายงานแบบอื่นด้วย · โหมดออนไลน์นับเฉพาะสิ่งที่ยังไม่ซิงก์
- **migration 005**: `form_docs`, `form_templates` (RLS ต่อโครงการ), `projects.zones` + `set_project_zones()` · ทดสอบ RLS ด้วย PGlite ผ่าน 143 ข้อ
