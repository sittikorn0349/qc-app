# qc-app — สรุปจุดแข็ง/จุดอ่อน (ฉบับสรุป)

repo: `sittikorn0349/qc-app` · สรุปจากการตรวจโค้ด production + beta ทั้งหมด · เอกสารนี้เป็นฉบับสรุปแยกจาก `qc-app-improvement-plan.md` (รายละเอียดเชิงเทคนิค/แผนแก้ไขทั้งหมดอยู่ในไฟล์นั้น)

## ภาพรวมใน 3 ประโยค

qc-app เป็น PWA ตรวจงานก่อสร้างที่มี**ฐานวิศวกรรมด้าน data integrity แน่นหนากว่าที่แอปขนาดนี้ควรจะมี** — verify-before-write, two-phase commit, 3-way merge ตอน sync ทำได้ดีกว่าคู่แข่งในตลาดหลายรายที่ไม่ได้โฆษณาความแน่นหนาระดับนี้เลย แต่กำลังเดินเข้าสู่ทิศทาง **ออนไลน์ล้วน + ฟีเจอร์ใหม่ (form builder, workflow) ที่ขยายเร็วกว่าที่โครงสร้างข้อมูลรองรับ** ทำให้จุดอ่อนที่ใหญ่ที่สุดไม่ใช่ความซับซ้อนของโค้ด แต่เป็น **เส้นแบ่งที่ไม่ชัดระหว่างสิ่งที่ "สำรอง/ซิงก์ครบ" กับ "ไม่ครบ"** ซึ่งผู้ใช้ไม่มีทางรู้ได้เองจากหน้าจอ

## จุดแข็ง

| จุดแข็ง | หลักฐาน | ความสำคัญ |
|---|---|---|
| **Verify-before-write ทุกการรับไฟล์** | SHA-256 ตรวจทุกไฟล์ก่อนนำเข้า ถ้าไม่ผ่านไม่เขียนอะไรเลยสักบรรทัด (`pwa-send.js`) | ป้องกันข้อมูลครึ่งๆกลางๆ ได้จริง ไม่ใช่แค่ทฤษฎี |
| **Two-phase commit + อ่านย้อนกลับตรวจซ้ำ** | หลัง commit ข้อมูลแล้วอ่านกลับมาเทียบ hash อีกรอบก่อนบอกว่า "สำเร็จ" | ตรวจจับความเสียหายจากความผิดพลาดของ storage เองได้ด้วย ไม่ใช่แค่ไฟล์จากภายนอก |
| **3-way merge ตอน sync ออนไลน์ (beta)** | merge แยกตาม field จริง ไม่ใช่ last-write-wins | แก้ปัญหาจริงของงานหลายคนแก้พร้อมกัน ซึ่งแอปคู่แข่งหลายรายยังใช้วิธี overwrite ง่ายๆ |
| **Armed-delete pattern** | กดลบครั้งแรก = เตือน, ครั้งสอง = ยืนยัน (มี timeout 3s) | ป้องกันลบพลาดโดยไม่ต้องขัด flow ด้วย modal |
| **Accessibility เกินมาตรฐานแอปงานก่อสร้างทั่วไป** | aria-label/aria-pressed/focus-visible ครบเกือบทุกจุดโต้ตอบ | แอปกลุ่มนี้ส่วนใหญ่มองข้าม accessibility ไปเลย |
| **ปุ่มหน้าแรกแบบ tile ใหญ่ 3×3** | ออกแบบมาให้กดด้วยนิ้วโป้งข้างเดียวได้ | เหมาะกับสภาพใช้งานจริงหน้าไซต์ (มือเดียว ต้องรีบ) |
| **ย่อรูป + ตรวจ MIME จาก byte signature ก่อนเชื่อไฟล์** | `shrink()`, `sniff()` ใน `index.html`/`pwa-send.js` | กันไฟล์รูปเพี้ยนและคุมขนาดไฟล์ได้โดยผู้ใช้ไม่ต้องทำเอง |

## จุดอ่อน (เรียงตามผลกระทบ)

| ระดับ | จุดอ่อน | หลักฐาน | ผลกระทบ |
|---|---|---|---|
| **CRITICAL** | เอกสารจาก form builder (`pwa-forms.js`) อยู่ในฐานข้อมูลแยก ไม่ถูกรวมใน backup/ส่งเอกสาร/sync เลย | ตรวจแล้วด้วย grep: ไม่มีจุดใดเชื่อม `qc-forms` กับ `buildBackup()`/`__qcDocs()` | ข้อมูลหายแบบผู้ใช้ไม่รู้ตัว ขัดกับคำมั่นสัญญาหลักของแอปเรื่อง backup |
| **CRITICAL** | ย้ายไปออนไลน์ล้วนโดยไม่มี "โหมดร่างก่อนมีโปรเจกต์" = เปิดแอปไม่ได้เลยถ้าเครื่องใหม่ไม่มีเน็ตตอนแรก | ต้อง Google OAuth login ก่อนทุกครั้งที่เป็นเครื่องใหม่ | ขัดกับจุดขายหลัก "ใช้ได้แม้ไม่มีเน็ตหน้าไซต์" ที่เป็นเหตุผลที่แอปนี้เกิดขึ้นมา |
| **HIGH** | การนำทางหน้าแรกผูกกับ regex จับข้อความสถานะภาษาไทย | `pwa-home.js` บรรทัด 223 | แก้คำในข้อความสถานะเมื่อไร นำทางพังทันทีแบบไม่มี error ให้เห็น |
| **HIGH** | ขั้นยืนยันการส่งไฟล์ (รหัส 8 หลัก) ไม่มีการ enforce ในแอป ต้องพึ่งผู้ใช้เทียบกันเอง | `pwa-send.js` บรรทัด 406 | ความแน่นหนาของ verify-before-write ทั้งหมดไม่ถูกใช้ประโยชน์จริงถ้าผู้ใช้ข้ามขั้นนี้ |
| **HIGH** | แถวรายการตรวจแต่ละแถวมี 6 ส่วนให้โต้ตอบ ไม่มีโหมดกรอกเร็ว | layout มือถือใน `index.html` | ฟอร์ม 20-30 รายการ = เลื่อนจอยาว ช้าลงหน้าไซต์จริง |
| **MEDIUM** | ตัวแปร `mode==='cloud'` สื่อความหมายผิดจากที่เกิดขึ้นจริง (คือ local ไม่ใช่ cloud) | `index.html` บรรทัด 680 | เสี่ยง bug ตอนรวม beta (ที่มี cloud จริง) เข้า production |
| **MEDIUM** | ปุ่มไอคอนบนรูป (28px) เล็กกว่าเกณฑ์จุดสัมผัสที่แนะนำสำหรับคนสวมถุงมือ | `.tb` บรรทัด 166 | กดพลาดง่ายกว่าค่าเฉลี่ย |
| **MEDIUM** | ตำแหน่งที่พบปัญหาเป็น free text ล้วน ไม่ pin บนแปลน | ฟิลด์ `loc` ทั้งระบบ | ความแม่นยำของตำแหน่งต่ำกว่าคู่แข่งในตลาด (Fieldwire, PlanRadar) |
| **MEDIUM** | ลงนามพิมพ์ชื่อเท่านั้น ไม่มีลายเซ็นวาดด้วยนิ้ว | ส่วน "สรุปผลและลงนาม" | น้ำหนักความน่าเชื่อถือของเอกสารต่ำกว่ามาตรฐานตลาด |
| **DESIGN FLAW** | ฟอร์มจาก form builder ไม่ปรากฏในคลังเอกสารเดียวกับฟอร์มตรวจงานหลัก | แยกฐานข้อมูล = แยกหน้าตา UI | ขัดกับโมเดลที่ README สื่อสารกับผู้ใช้ไว้เองว่า "คลังเอกสาร" คือที่เดียว |

## คำตัดสินสุดท้าย

ระบบ**เหมาะสมกับ use case ปัจจุบัน** (ทีมเล็ก ใช้งานออฟไลน์เป็นหลัก) และมีฐานวิศวกรรมที่ดีกว่าที่ผู้ใช้ทั่วไปจะสังเกตเห็น แต่กำลังขยายฟีเจอร์ (online mode, form builder, workflow) **เร็วกว่าที่โครงสร้าง backup/sync รองรับ** — ก่อนเพิ่มฟีเจอร์ใหม่ใดๆต่อ ต้องปิดช่องว่าง CRITICAL 2 ข้อก่อน (form builder หลุดจาก backup, และถ้าจะไปออนไลน์ล้วนต้องมีโหมดร่างก่อนมีเน็ต) ไม่เช่นนั้นทุกฟีเจอร์ใหม่จะขยายขนาดของปัญหาเดิมให้ใหญ่ขึ้นไปอีก

รายละเอียดเชิงเทคนิคของแต่ละข้อ รวมถึงทิศทางแก้ไขและแผนลำดับงาน อยู่ในไฟล์ `qc-app-improvement-plan.md`
